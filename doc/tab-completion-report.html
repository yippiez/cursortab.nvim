How Tab Completion Works in cursortab.nvim

A walk through the model-completion pipeline — and exactly how the prompt tokens are defined and assembled.

cursortab is a Neovim edit-completion plugin. A thin Lua layer in the editor talks to a Go server (the daemon) over RPC. The server gathers context, builds a model prompt out of carefully defined token markers, calls a completion model over an OpenAI-style API, then turns the raw text back into staged, accept-able edits. This report covers that round trip end to end.

1 · The pipeline, step by step

One keystroke (or a manual trigger) flows through these stages. Steps 1–6 happen in the editor/engine, 7–10 are provider-side prompt & model work, and 11–14 turn the answer into visible edits.

Event arrives

server/engine/events.go

A buffer change, idle timer, or manual Ctrl-Space raises an event. Automatic triggers are debounced; a manual trigger sets a manual flag that bypasses suppression.

Gating / suppression

server/engine/request.go · suppress.go

Cheap checks decide whether it's even worth calling the model: no edits since save, cursor in a disabled treesitter scope, mid-line with meaningful suffix, a single-char deletion (typo fix), or a match against the recently-rejected cache.

Capture the snapshot

server/ctx/model.go · CurrentSnapshot

The current buffer state is frozen: WorkspacePath, File.Path/Lines, 1-indexed Cursor.Row, 0-indexed Cursor.Col, and viewport bounds.

Collect context materials

server/ctx/materials.go

Each provider declares what it needs. The engine collects only those: treesitter scope, recent-file retrieval chunks, edit/diff history, git diff, diagnostics, recent user actions — and the project TAB.md.

Pick & dispatch the provider

server/engine/engine.go · provider/flow.go

The configured provider (fim, sweep, zeta, inline, …) is invoked via Complete() (batch) or StreamCompletion() (streaming).

Build the request window

server/provider/flow.go · RequestWindow

The buffer is trimmed to a window around the cursor (bounded by context size, snapped to treesitter ranges). This window is what the model actually sees: Window.Lines, Window.Start, Window.CursorLine.

Build the prompt

provider/fim/fim.go · sweep/sweep.go · Build()

The provider assembles the token-delimited prompt string (see §3–§5). This is where the FIM / sweep markers get stitched around your code.

Call the model

server/client/openai/openai.go

An OpenAI-style CompletionRequest (prompt, optional suffix, stop tokens, temperature, max tokens) is POSTed. Batch returns a full string; streaming yields lines.

Parse & sanitize

provider Parse() · provider/processors.go

Stop markers are stripped, repetition rejected, suffix-overlap trimmed (FIM), and oversized output is anchor-truncated and validated against the original window.

Compute the diff

server/text/diff.go · ComputeDiff

A Myers diff between the original window and the model's text yields line-level changes plus an old↔new line mapping.

Split into stages

server/text/staging.go · CreateStages

Changes are grouped by proximity and viewport into ordered stages, sorted nearest-cursor-first. Far-away first edits are flagged as needing a navigation jump.

Render → accept/reject

server/engine/completion.go · accept.go

The stage is rendered as an inline diff. Tab applies it and advances to the next stage (or jumps the cursor / prefetches the next prediction); Esc rejects and may cache the rejection.

2 · How the tokens are defined

"Tokens" here means the special marker strings that delimit regions of the prompt — not model sub-word tokens. There are two families: configurable FIM tokens (set per-model in Lua) and hard-coded provider markers (baked into a provider's prompt format).

2.1 · FIM tokens — configured per model

server/types/types.go · FIMTokenConfig  ↔  lua/cursortab/config.lua · fim_tokens

// Go: server/types/types.go
type FIMTokenConfig struct {
    Prefix   string // before the prefix content   e.g. "<|fim_prefix|>"
    Suffix   string // before the suffix content   e.g. "<|fim_suffix|>"
    Middle   string // before the completion       e.g. "<|fim_middle|>"
    RepoName string // OPTIONAL repo header token   e.g. "<|repo_name|>"
    FileSep  string // OPTIONAL file separator      e.g. "<|file_sep|>"
}

Two important switches. (a) If fim_tokens is omitted entirely, the FIM provider falls back to OpenAI prompt+suffix mode (e.g. DeepSeek) — no marker tokens at all. (b) The cross-file context block is only built when both repo_name and file_sep are set. For Qwen/zeta models these are auto-filled to <|repo_name|> / <|file_sep|> if you leave them blank (config.lua).

3 · FIM prompt assembly — two modes

server/provider/fim/fim.go · Build()

The provider first splits the window into prefixContent (everything up to the cursor) and suffixContent (everything after). What happens next depends on whether fim_tokens is set.

Mode A — prompt + suffix tokens == nil

OpenAI completions style (DeepSeek & co). No markers; the API gets two fields.

// cursor in: "hello| world"
CompletionRequest{
  Prompt: "hello",
  Suffix: " world",
  Stop:   nil,
}

Mode B — tokenized FIM tokens != nil

Markers wrap the two halves; the model continues after Middle.

<PRE>hello<SUF> world<MID>▏…model fills here…

Stop: ["<PRE>","<SUF>","<MID>"]

The assembled order in Mode B is literally: Prefix → prefixContent → Suffix → suffixContent → Middle. When repo tokens are configured, the cross-file block is prepended before all of it.

4 · Sweep prompt assembly — the 3-section format

server/provider/sweep/sweep.go · Build()

Sweep is an edit (next-edit) provider, not fill-in-the-middle. It shows the model the same code window three times — as it was, as it is (with a cursor marker), and an empty updated slot to rewrite — preceded by context sections.

<|file_sep|>main.go
…~300 lines of broad file context around the cursor…

<|file_sep|>context/docs          ← TAB.md project doc
Use the run_py helper for python.

<|file_sep|>context/retrieval  ← recent-file chunks
<|file_sep|>context/treesitter ← scope / siblings / imports
<|file_sep|>context/diagnostics← LSP errors
<|file_sep|>context/staged_diff← git diff

<|file_sep|>original/main.go:10:20    ── the window, untouched
def greet(name):
    print(name)

<|file_sep|>current/main.go:10:20     ── same window + cursor marker
def greet(name):
    print(<|cursor|>name)

<|file_sep|>updated/main.go:10:20     ── model rewrites here
def greet(name):                  ← "prefill": lines before the
    print(▏…model continues…           cursor are pre-written so the
                                    model only emits the edit
Prefill. The updated/ section isn't empty — sweep pre-writes the lines up to the edit point (computePrefill) so the model only generates the change, not the whole window. In insertion mode (a recent insert above the cursor) only the first line + trailing blanks are prefilled, giving the model freedom to re-flow shifted lines.

5 · The cross-file context block

Both providers prepend project context. Sweep emits context/* sections (above); FIM builds an equivalent repo block in buildRepoContext (only when repo_name + file_sep are set). Same information, provider-specific framing:

TAB.md is read by server/tabmd/tabmd.go — Read(workspacePath), capped at 4096 bytes, placed early so it stays stable across edits (good for prompt caching).

6 · The wire request & stop tokens

server/client/openai/openai.go · CompletionRequest

type CompletionRequest struct {
    Model       string   // config.provider.model
    Prompt      string   // assembled in §3–§5
    Suffix      string   // only in FIM prompt+suffix mode
    Temperature float64
    MaxTokens   int
    TopK        int
    Stop        []string // the provider's stop tokens (§2.3)
    N           int      // always 1
    Echo        bool     // always false
    Stream      bool     // true on the streaming path
}

The provider base fills Model, Temperature, MaxTokens, TopK from config (provider.openai.go · Request()); the provider passes Prompt and Stop. On the streaming path the same request is cloned with Stream:true and lines are consumed as they arrive.

7 · After the model — diff → stages → accept

The raw completion is just text. Turning it into reviewable edits:

Sanitize

provider Parse()

Strip <|file_sep|>/<|endoftext|>, reject empties & repetition, trim suffix overlap (FIM regenerating the tail), drop a truncated last line.

Anchor-truncate & validate

provider/processors.go

If output hit the length limit, truncate to the last line that still anchors to the original — and reject if it shrank the window too much.

Diff

text/diff.go

Myers diff of original-window vs. completion → line changes + line mapping.

Stage

text/staging.go

Cluster changes by proximity/viewport into ordered stages; nearest-to-cursor first; flag far first-edits for a navigation jump.

Render

engine/completion.go

Show the current stage as an inline diff; snapshot metrics; register the stage as a rejection candidate.

Accept / advance / reject

engine/accept.go

Tab applies and advances to the next stage, jumps to a cursor target, or kicks a prefetch for the next prediction. Esc clears (and may remember the rejection for ~30s).

Why stages? A single model answer can touch several disjoint spots. Rather than apply a big multi-line blob at once, cursortab walks you through the edits one cluster at a time, jumping the cursor between them — so each Tab is a small, reviewable step.
